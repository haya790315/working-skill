# design プラグイン

要求調査から振り返りまで、設計・報告工程を **17 の成果物**に分けて進めるスキル集です。

**このプラグインは文書だけを作ります。**コードの実装・修正・実行は一切行いません
（調査のためにコードを読むことはします）。実装は `develop` プラグインの担当です。

大きな設計書を一つ作るのではなく、**工程ごとに文書を分けます。**
一つの文書に全部詰め込むと、読み手は自分に関係のある部分を探せず、
書き手は「どこまで書けば終わりか」を判断できなくなるためです。

## 使い方

### どのレポートを書けばいいか分からないとき

```
/design:navigate ユーザーが注文をキャンセルできるようにしたい
```

やりたいことを自然文で渡すと、**必要なレポートと順序**を提示します。
既に `docs/design/<slug>/` があれば、**足りない文書と食い違い**も診断します。
文書は作りません。案内だけです。

判断がつかない点は**収束型の質問**で詰めます。ただし grill-me とは違い、
**推奨は最初から提示され、質問はそれを鋭くするだけ**です。1 問答えるごとに
推奨が更新され、毎回「ここで確定してよいですか」が付くので、途中で打ち切っても
使える答えが残ります。上限 6 問、分類が明確なら 0 問。

**要件そのもの（利用者・画面・データ）は聞きません。**それは `02` の仕事で、
ここで聞くと 02 で同じことをもう一度聞かれることになります。

### 案件を始めるとき

```
/design:00-start
```

モード（新規 / 機能追加）と対象を決め、
`docs/design/<slug>/00-index.md` を作ります。以降の工程はこのファイルを読んで動きます。

工程は**自動では連鎖しません。**各工程が終わったら、次のコマンドを自分で実行します。
1 工程 1 会話にすることで、その工程に必要な文書だけを読んだ状態で作業できます。

各スキルの末尾には **`## 次の工程`** があり、その工程の結果に応じて
次に実行すべきコマンドが条件付きで示されます。順番を覚える必要はありません。

## 機能を過不足なく説明する最小セット

17 個すべてを書く案件はほとんどありません。**その機能を説明しきるために最低限必要なのは、
次の 4 つの問いに答えることです。**

| 問い | 答えるレポート | これが無いと |
| --- | --- | --- |
| 何を作るのか | `02-requirements-analysis` | 完了判定ができない |
| どう作るのか | `05-architecture-design` | 実装者が毎回設計し直す |
| 何が壊れるのか | `07-impact-analysis` | リリースで事故る |
| どう確かめるのか | `11-test-plan` | 「動いた」の基準が人によって違う |

`新規` なら **02・05・11**、`機能追加` なら **02・07・11** が最小セットです。
残りは必要になったときに足します。判断に迷ったら `/design:navigate` に聞いてください。

## 工程一覧

| # | コマンド | 成果物 | 何をするか |
| --- | --- | --- | --- |
| — | `/design:navigate` | なし | **どのレポートが要るかを案内・診断。工程ではない** |
| 00 | `/design:00-start` | `00-index.md` | モード判定、slug 決定、実施工程の選定 |
| 01 | `/design:01-requirements-investigation` | 要求調査報告書 | 要望と現状を集める。分析はしない |
| 02 | `/design:02-requirements-analysis` | 要件定義書 | 要望を検証可能な要件に変換。**用語定義の source of truth** |
| 03 | `/design:03-feasibility-study` | 実現可能性調査報告書 | 技術・スケジュール・体制・コストの 4 軸で複数案を比較 |
| 04 | `/design:04-technical-investigation` | 技術調査報告書 | 候補技術を同一基準で横並び比較 |
| 05 | `/design:05-architecture-design` | アーキテクチャ設計書 | 構成・責務・データモデル・I/F を mermaid で図示 |
| — | `/design:adr` | `docs/adr/NNNN-*.md` | 重要な決定を独立記録。**工程ではなく随時実行** |
| 06 | `/design:06-poc` | PoC 報告書 | 検証前に成功基準を確定し、検証後に結果をまとめる |
| 07 | `/design:07-impact-analysis` | 影響範囲分析書 | 変更の波及先をコード調査で洗い出す |
| 08 | `/design:08-security-review` | セキュリティレビュー報告書 | 観点表に沿って確認し、検出事項を深刻度別に整理 |
| 09 | `/design:09-risk-assessment` | リスク評価書 | 影響度 × 発生確率で評価し、対応方針と担当・期限を決める |
| 10 | `/design:10-development-plan` | 開発計画書 | 縦切りタスクへ分解。**計画書のみ。実装はしない** |
| 11 | `/design:11-test-plan` | テスト計画書 | テストレベル・観点・合否基準。**受入基準と全件対応** |
| 12 | `/design:12-release-migration-plan` | リリース・移行計画書 | 当日手順、データ移行、**切り戻し判断基準** |
| 13 | `/design:13-progress-report` | 進捗報告書 | 上長・関係者向け。**要判断事項が主役**。随時 |
| 14 | `/design:14-performance-report` | 性能測定報告書 | 非機能要件の目標値と実測を対比。随時 |
| 15 | `/design:15-rca` | 障害根本原因分析報告書 | 問題発生時のみ。仕組みの原因まで掘る。随時 |
| 16 | `/design:16-retrospective` | 振り返り報告書 | KPT。**Try に担当と期限を付ける**。随時 |

`随時` の工程は順番を持ちません。必要になったときに何度でも実行できます。

```

    ├── 01-requirements-investigation.md
    ├── 02-requirements-analysis.md
    ├── 03-feasibility-study.md
    ├── 04-technical-investigation.md
    ├── 05-architecture-design.md
    ├── 06-poc/<NN>-<topic>.md               ← 複数回
    ├── 07-impact-analysis.md
    ├── 08-security-review.md
    ├── 09-risk-assessment.md
    ├── 10-development-plan.md
    ├── 11-test-plan.md
    ├── 12-release-migration-plan.md
    ├── 13-progress/YYYY-MM-DD.md            ← 複数回
```

ADR だけ `docs/design/` の外に出しています。ADR は特定の案件ではなく
**リポジトリ全体に対して長期間効く**決定であり、案件ディレクトリに埋めると
必要なときに見つけられなくなるためです。

## 2 つのモード

`00-start` が判定し、`00-index.md` に記録します。各工程はこの値を読んで**対象範囲を絞ります**。
処理の流れ自体は変わりません。

| モード | 対象 | 既定で実施する工程 |
| --- | --- | --- |
| `新規` | システム全体 | 01〜05, 08〜12 |
| `機能追加` | 既存システムへの差分のみ。既存仕様は前提として扱い再定義しない | 01, 02, 07, 10, 11 |

既定値は提示されるだけで、増減できます。

## 全工程に共通するルール

- **文書のみを作成する。**コードの実装・修正・実行はしない。調査のために読むのは可
- **調べられる事実は自分で調べる。**ユーザーに聞くのは「判断」だけ
- **質問は 1 回に 1 問、推奨案を添える。上限 6 問**
  — 上限は「調べる前に聞く」ことを防ぐための予算。**超えた分を推測で埋めるのは禁止**で、
  未解決として文書に明記する。毎回 6 問に達する工程があれば、それは工程の分担か
  上流成果物の不足を疑うサイン
- **章立ては固定。**増減しません。下流工程が特定の章を読みに来るためです
- **文体は敬体。**ファイル名は英語、本文は日本語
- **図は mermaid。**テキストなので差分が追えます
- **決まらなかったことは `未決事項` に残す。**上流の宿題は下流工程が拾います
- **逆転コストが高く代替案が実在する判断は `/design:adr` へ**
- **その工程の担当でない問いに、その場で答えを出さない**（下記）

## 質問の帰属 — 工程をまたぐ問いの扱い

作業中に「これは今の工程で決めることじゃないな」という問いが出てきたときの規則です。
**その場で答えを出してはいけません。**帰属先で処理します。

| 気づいたこと | やること |
| --- | --- |
| 前工程で決まっているべきだった | **その工程の成果物に戻って追記**し、`00-index.md` の更新履歴に記録する |
| 後工程で決めること | `未決事項` に、**どの工程が決めるか**を添えて残す |

理由は 2 つあります。

**前工程の漏れを黙って埋めると、その判断は誰にも共有されません。**
たとえば `11-test-plan` を書いていて「この受入基準、判定できないな」と気づいたとき、
その場で基準を書き換えてしまうと、`02` を読んだ人は古い基準のままだと思い続けます。
`02` に戻って直せば、`10` のタスク対応も一緒に見直せます。

**後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。**
`05-architecture-design` の最中に「リリースは段階的にするか」を決めても、
`12-release-migration-plan` が持つ影響範囲や停止可能時間の情報が無い状態での判断です。
`未決事項` に「`12` で決める」と書いて渡すほうが、良い判断になります。

## 3 本の縦串

工程をまたいで整合を保つ仕組みが 3 つあります。

- **用語定義** — `02` の `用語定義` が唯一の術語源。03 以降は必ずここに合わせ、
  新しい用語が要るときは 02 に追記します
- **受入基準** — `02` の `受入基準` が `10` のタスク対応、`11` のテスト観点対応に紐づきます。
  どちらも**全件埋める**ことを求めており、埋まらない基準は分解漏れか検証不能な基準です
- **非機能要件** — `02` の `NFR-ID` が `05` の対応方針、`11` の検証方針、`14` の目標値へ流れます

## 未決事項とリスクの流れ

上流で決まらなかったことが下流で拾われる経路も決まっています。

```
03 前提条件とリスク ─┐
06 残課題          ─┤
07 未調査の領域     ─┼→ 09 リスク評価 → エスカレーション基準
08 検出事項        ─┘
                    15 RCA 恒久対策 ─┘
```
