# リリース・移行計画

**本番に出す作業を、当日困らない粒度まで書き下す**工程です。

この計画書で最も重要な章は手順ではありません。**切り戻しの判断基準**です。
「問題があったら戻す」は基準ではありません。誰が、何を見て、いつまでに、
どうなったら戻すと決めるのか——それが決まっていない計画は、
当日その場で判断することになり、判断が遅れます。

手順は**別の人が読んで実行できる粒度**で書きます。書いた本人が当日いる前提にしません。

## 共通ルール

0. **本スキルは文書のみを作成します。**リリース作業の実行、デプロイ、コードや設定の変更は行いません。既存の手順・設定を調査のために読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、モードと対象範囲を把握します。無い場合は `/design:00-start` の実行を促して停止します。
2. `07-impact-analysis.md` の `後方互換性` `リリース順序`、`10-development-plan.md` の `リリース手順`、`11-test-plan.md` の完了条件を読みます。
3. **既存のリリース運用はリポジトリと設定から自分で調べます**（CI/CD 設定、デプロイスクリプト、環境構成、マイグレーションの仕組み）。ユーザーには聞きません。
4. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。停止可能時間・実施日・承認者は必ず本人に確認します。
5. 文体は敬体。図は mermaid。章立ては下記から増減しません。
6. 書き終えたら `00-index.md` のステータスを更新し、次工程を案内します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## リリース方式の選択

| 方式 | 向いている場面 | 代償 |
| --- | --- | --- |
| 一括切替 | 影響が小さい、停止時間を取れる | 問題時の影響が全利用者に及ぶ |
| 段階リリース | 利用者が多い、影響を測りながら広げたい | 新旧が併存する期間の整合を設計する必要がある |
| ブルーグリーン | 短時間で戻したい | 環境を二重に持つコスト |
| フィーチャーフラグ | コードは出すが機能は隠したい | フラグの後始末を計画に含める必要がある |

**選んだ理由と、選ばなかった方式の理由**を書きます。

## データ移行がある場合の必須事項

- **移行前後の件数照合方法** — 「移行できた」を何で判定するか
- **移行にかかる実測時間** — 本番相当のデータ量でのリハーサル結果
- **移行中に業務が動く場合の整合** — 止められないなら差分取り込みの設計が要ります
- **移行の切り戻し** — **データは戻せないことが多い**。戻せないなら、それを明記して承認を得ます
