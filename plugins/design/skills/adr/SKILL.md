# ADR（アーキテクチャ決定記録）

**これは工程ではありません。**番号を持たないのはそのためです。
決定は工程の途中で起きます。要件分析中に「オフライン対応はしない」と決めることも、
詳細を詰めている最中に「楽観ロックを使う」と決めることもあります。
どの工程にいても、決まった瞬間に書きます。

**本スキルは文書のみを作成します。**コードの実装・修正・実行は行いません。
決定の背景を確認するためにコードを読むことはします。

## `未決事項` との使い分け

各工程の設計書にある `未決事項` と ADR は補完関係です。境界は厳密に守ります。

| | 状態 | 置き場所 |
| --- | --- | --- |
| 未決事項 | **まだ決まっていない** | 各工程の設計書の中。下流工程に引き継ぐ |
| ADR | **決まった。ただし代償がある** | `docs/adr/` に独立ファイル |

## 起票の判定基準（3つすべて満たすこと）

1. **逆転コストが高い** — 後で気が変わったときの変更コストが大きい
2. **文脈なしでは意外に見える** — 将来の読み手がコードを見て「なぜこうした？」と思う
3. **実在するトレードオフの結果** — 本当に選択肢があり、理由があって一方を選んだ

**1つでも欠けたら ADR にしません。**簡単に覆せるなら覆せばよく、意外でないなら誰も疑問に思わず、
代替案が無かったなら記録すべきことは何もありません。この閾値を緩めると、
「何でも ADR」になって誰も読まなくなります。

### 該当する例

- **構成の形** — 「モノレポにする」「書き込みモデルはイベントソーシングにする」
- **ロックインを伴う技術選定** — DB、メッセージバス、認証基盤。**ライブラリ全部ではなく、乗り換えに四半期かかるものだけ**
- **境界とスコープの決定** — 「顧客データは顧客コンテキストが所有し、他は ID 参照のみ」。**やらないと決めたことも同じ価値があります**
- **あえて定石を外した判断** — 「ORM ではなく手書き SQL を使う。理由は〜」。次の担当者が「直そう」としてしまうのを防ぎます
- **コードに現れない制約** — 「コンプライアンス上 AWS を使えない」「提携先 API の契約により応答は 200ms 以内」

## 手順

1. **既存 ADR を確認する** — `docs/adr/` を走査し、同じ話題の ADR が無いか見ます。あって内容が変わるなら、
   古いものを編集せず**新しい ADR を起こし、古い方に `Superseded by ADR-NNNN` を付けます**。ADR は追記のみで、書き換えません。
2. **番号を採る** — `docs/adr/` の最大番号 + 1。4 桁ゼロ埋め。ディレクトリが無ければここで作ります。
3. **書く** — `docs/adr/NNNN-<英語スラッグ>.md`。
4. **リンクする** — `docs/design/<slug>/00-index.md` の `関連 ADR` に追記します。

## テンプレート

```md
# {決定の短いタイトル}

{状況・決定・理由を 1〜3 文で。これだけで成立します。}
```

**1 段落で構いません。**価値は「決定があったこと」と「なぜか」が残ることであって、
章を埋めることではありません。

### 任意の章（本当に価値があるときだけ）

- **Status**（frontmatter） — `proposed` / `accepted` / `deprecated` / `superseded by ADR-NNNN`
- **検討した代替案** — 却下した案を覚えておく価値があるときだけ
- **影響** — 自明でない波及がある場合だけ

本文は日本語・敬体で書きます。`docs/adr/` は `develop` プラグインと共用のため、
ディレクトリ・採番・テンプレート構造は変えません。

## 次の工程

ADR は工程ではないため、**元の工程に戻ります。**`00-index.md` の `関連 ADR` に追記したら、
中断していた工程のコマンドを再実行するか、その場の作業を続けてください。

決定内容が既存の成果物と食い違う場合は、該当する成果物を更新してから先に進みます。
