# 設計パイプライン起動

`design` プラグインの入口です。**成果物は作りません。**この工程がやるのは、
「どのモードで」「どの工程を」「どこに」進めるかを決めて `00-index.md` に書き残すことだけです。

以降の各工程はこのファイルを読んで動きます。ここが唯一の状態源です。

**どの工程が必要か自体が決まっていない場合は、先に `/design:navigate` を実行してください。**
やりたいことを自然文で渡すと、必要なレポートと順序を提示します。

## 手順

### 1. モードを推定する

ユーザーに空で聞かず、まず環境を調べてから確認します。

| 環境 | 推定モード |
| --- | --- |
| ソースコードあり / git 履歴あり | `機能追加` |
| 空のリポジトリ / コードなし | `新規` |

推定結果を提示し、違っていたら直してもらいます。

### 2. slug を決める

対象を表す英小文字ケバブケースの短い識別子です。現在のブランチ名やユーザーの説明から
候補を 1〜2 個出して確認します（例：`order-cancel`、`sso-integration`）。

下表を**既定値として提示**し、増減してもらいます。全工程を強制しません。

### 4. `00-index.md` を作る

`docs/design/<slug>/00-index.md` を下記の章立てで作成します。章は増減しません。

- **プロジェクト概要** — 1〜3 行。何を作るのか。
- **モード** — `新規` または `機能追加`。以降の全工程がこの値で対象範囲を決めます。
- **対象範囲** — 対象システム・対象機能。`機能追加` の場合は差分の範囲。
- **関係者・報告先** — 意思決定者、レビュー担当、報告先。空欄可。
- **工程一覧** — 表：`# / 工程 / 成果物パス / ステータス / 更新日`。
  ステータスは `未着手` `作成中` `レビュー待ち` `完了` の4つのみ。
- **関連 ADR** — `docs/adr/` に生まれた ADR の番号とタイトル。最初は空。
- **更新履歴** — 表：`日付 / 更新内容 / 更新者`。

### 5. 最初の工程を案内する

「今から最初の工程を始めますか」と一度だけ聞きます。始める場合はそのコマンドを実行します。

## 次の工程

| 状況 | 次に実行するコマンド |
| --- | --- |
| 要望の整理から始める | `/design:01-requirements-investigation` |
| 要望は既に明確、すぐ要件化できる | `/design:02-requirements-analysis` |
| 障害対応で来た | `/design:15-rca` |

## ルール

- **本プラグインの全スキルは文書のみを作成します。**コードの実装・修正・実行は行いません。調査のためにコードを読むことはします。
- 文体は敬体（です・ます）。ファイル名は英語、本文は日本語。
- 既に `00-index.md` がある場合は上書きせず、内容を提示して差分だけ更新します。
- 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。
