# セキュリティレビュー

設計と実装方針を**観点表に沿って一つずつ確認し、結果を残す**工程です。

セキュリティレビューが形だけになる原因は、**「問題なし」の根拠が書かれないこと**です。
「認証：問題なし」では、見た上で問題ないのか、見ていないのかが区別できません。
**全観点に「何を確認してそう判断したか」を書きます。**該当しない観点は「対象外」と理由を書きます。

## 共通ルール

0. **本スキルは文書のみを作成します。**コードの実装・修正・実行、攻撃・侵入テストの実施は行いません。調査のためにコードや設定を読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、モードと対象範囲を把握します。無い場合は `/design:00-start` の実行を促して停止します。
2. `02-requirements-analysis.md` の `用語定義` と非機能要件のセキュリティ項目、`05-architecture-design.md` の構成、`07-impact-analysis.md` の影響範囲を読みます。
3. **確認はコードベースと設計文書の調査で行います。**ユーザーに聞くのは、社内規定・法令要件・過去の指摘事項など文書から読めないものだけです。
4. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。
5. 文体は敬体。章立ては下記から増減しません。
6. 検出事項はリスクとして `/design:09-risk-assessment` に引き渡します。設計判断を変える場合は `/design:adr` を促します。
7. 書き終えたら `00-index.md` のステータスを更新し、次工程を案内します。

観点の一覧は [SECURITY-CHECKLIST.md](SECURITY-CHECKLIST.md) を使います。**全項目に目を通します。**

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## 深刻度の判定

| 深刻度 | 基準 | 対応 |
| --- | --- | --- |
| `高` | 情報漏洩・改ざん・不正操作に直結する | リリース前に必須対応 |
| `中` | 他の条件と組み合わせると被害につながる | 期限を決めて対応 |
| `低` | 直ちに被害はないが望ましくない | 対応方針を決めて記録 |

**`高` を残したままリリースする場合は、必ず承認者を明記します。**
判断した人が記録に残らないことが、最も避けたい状態です。

## 成果物

`docs/design/<slug>/08-security-review.md`

| 章 | 書くこと |
| --- | --- |
| レビューの目的と範囲 | 何を対象にしたレビューか。対象外も明記。 |
| 前提条件 | 扱うデータの機微度、想定する脅威、適用される社内規定・法令。 |
| 観点別の確認結果 | 表：`観点 / 確認内容 / 結果 / 根拠`。結果は `問題なし` `要対応` `対象外`。**根拠欄を空にしません。** |
| 検出事項 | 表：`ID / 内容 / 深刻度 / 該当箇所 / 想定される被害 / 推奨対応`。ID は `SEC-01` から。 |
| 個人情報・機微情報の取り扱い | 対象データ、保存場所、保持期間、アクセス権、マスキング方針。 |
| 対応方針 | 表：`SEC-ID / 対応方針 / 担当 / 期限 / 完了確認方法`。 |
| 受容する事項 | 対応しないと判断したもの。**理由と承認者を明記します。** |
| 次回レビューの契機 | どうなったら再レビューするか。 |
| 未決事項 | 決まらなかったこと。 |
