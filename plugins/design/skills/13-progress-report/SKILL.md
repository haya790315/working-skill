# 進捗報告

**読み手は忙しい人です。**冒頭 3 行で状況が掴めなければ、その報告書は読まれません。

進捗報告で本当に価値があるのは「終わったことの一覧」ではありません。
**判断や支援を求める事項**です。ここが空の報告は、単なる作業記録です。
問題が無いなら「無い」と明記します。

## 共通ルール

0. **本スキルは文書のみを作成します。**コードの実装・修正・実行は行いません。実績確認のためにコードや履歴を読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、工程の進捗状況と関係者・報告先を把握します。
2. `10-development-plan.md` があればタスク一覧を読み、それを進捗の単位にします。
3. **実績は自分で調べます。**git のコミット履歴、変更されたファイル、issue の状態、テストの通過状況。ユーザーに「何が終わりましたか」と聞く前に、まず調べた結果を提示して補ってもらいます。
4. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。
5. 文体は敬体。章立ては下記から増減しません。
6. 報告期間は前回の報告日から今日まで。前回が無ければユーザーに確認します。
7. 書き終えたら `00-index.md` の更新履歴に追記します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## 書き方の原則

- **サマリは 3 行以内。**「予定通り」「1 件遅延、対応中」「判断待ち 1 件」のような密度で
- **進捗率は根拠のある数字だけ。**タスク単位の完了数から出します。感覚の「70%」は書きません
- **遅延は隠さず、原因と挽回策をセットで書きます。**遅延の報告が遅れることが最大の問題です
- **状態は 4 値**：`予定通り` / `遅延` / `完了` / `未着手`

## 成果物

`docs/design/<slug>/13-progress/YYYY-MM-DD.md`
（ディレクトリが無ければ作成。ファイル名は報告日）

| 章 | 書くこと |
| --- | --- |
| 報告概要 | 表：`報告日 / 報告期間 / 報告者 / 報告先`。 |
| サマリ | **3 行以内。**全体状況、特筆事項、要判断の有無。 |
| 進捗状況 | 表：`タスクID / タスク / 状態 / 進捗率 / 備考`。`10-development-plan.md` のタスク一覧に対応させます。 |
| 今期間の完了事項 | 箇条書き。**成果物ベースで書きます**（「〜を実装した」ではなく「〜ができるようになった」）。 |
| 次期間の予定 | 箇条書き。着手予定のタスク ID を添えます。 |
| 課題・懸念 | 表：`内容 / 影響 / 対応 / 期限 / 担当`。無ければ「特になし」と明記。 |
| 判断・支援が必要な事項 | **この章がこの報告書の主役です。**表：`内容 / 必要な判断 / 期限 / 依頼先`。無ければ「特になし」と明記。 |
