# テスト計画

**何をもって「品質を確認できた」と言うのか**を、テストを始める前に決める工程です。

テスト計画の価値は網羅性の宣言ではありません。**受入基準との対応表**です。
`02` で決めた受入基準が一件ずつテスト観点に紐づいていて、
紐づかない基準が無い——これが確認できて初めて計画として成立します。

対応表が埋まらない受入基準が出たら、**それは検証不能な基準です。**
`02` に戻って基準を書き直すか、`未決事項` に上げます。曖昧なまま先に進めません。

## 共通ルール

0. **本スキルは文書のみを作成します。**テストコードの実装、テストの実行は行いません。既存テストを調査のために読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、モードと対象範囲を把握します。無い場合は `/design:00-start` の実行を促して停止します。
2. `02-requirements-analysis.md` の `受入基準` `非機能要件` `用語定義`、`07-impact-analysis.md` の影響範囲、`10-development-plan.md` のタスク一覧を読みます。
3. **既存のテスト構成はリポジトリから自分で調べます**（テストの置き場、命名、実行方法、CI 設定）。ユーザーには聞きません。
4. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。合否判定基準は必ず本人に確認します。
5. `機能追加` モードでは、**新規テストだけでなく既存テストへの影響**（`07` で洗い出した壊れるテスト）も範囲に含めます。
6. 文体は敬体。章立ては下記から増減しません。
7. 書き終えたら `00-index.md` のステータスを更新し、次工程を案内します。

テストレベルの定義と使い分けは [TEST-LEVELS.md](TEST-LEVELS.md) を参照します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## テスト観点の書き方

観点は「どこをテストするか」ではなく、**「何が起きたら困るか」**で挙げます。

- 悪い：`注文APIのテスト`
- 良い：`在庫が0のときに注文が成立しないこと`

観点には `TV-01` から ID を振り、優先度（`高` `中` `低`）を付けます。
**正常系だけの観点表は不完全です。**異常系・境界値・同時実行を必ず含めます。

## 成果物

`docs/design/<slug>/11-test-plan.md`

| 章 | 書くこと |
| --- | --- |
| テストの目的と完了条件 | 何が確認できたら完了か。**「全テスト通過」ではなく、判定可能な条件で。** |
| テストレベルと範囲 | 表：`レベル / 対象 / 担当 / 環境 / 実施時期`。 |
| テスト観点一覧 | 表：`ID / 観点 / 対象レベル / 優先度 / 備考`。ID は `TV-01` から。 |
| 受入基準との対応 | 表：`AC-ID / 受入基準 / 対応する観点ID`。**02 の受入基準を全件埋めます。**空欄は計画の欠陥です。 |
| 非機能要件の検証方針 | 表：`NFR-ID / 検証方法 / 担当`。性能は `14-performance-report` に引き渡します。 |
| 既存テストへの影響 | `07` で洗い出した、修正・追加が必要な既存テスト。 |
| テストデータ方針 | 何を使うか。**本番データを使う場合はマスキング方針を明記します。** |
| テスト環境 | 環境構成、本番との差異、その差異が結果に与える影響。 |
| 合否判定基準 | 何件までなら合格とするか。深刻度別の扱い。判定者。 |
| テストしない範囲 | やらない範囲と理由。**明記されない限り、やらないことは伝わりません。** |
| 未決事項 | 決まらなかったこと。 |
