# テストレベルの定義と使い分け

## 4 つのレベル

| レベル | 検証すること | 主な担当 | 環境 |
| --- | --- | --- | --- |
| 単体テスト | 個々のモジュールが仕様どおり動くこと | 開発者 | 開発環境 |
| 結合テスト | モジュール間・外部システムとの連携が成立すること | 開発者 / テスト担当 | 検証環境 |
| システムテスト | システム全体が要件を満たすこと（機能・非機能） | テスト担当 | 検証環境（本番相当） |
| 受入テスト | 利用者・業務部門が業務として使えると判断できること | 利用部門 | 受入環境 |

## どのレベルに割り当てるか

観点を上のレベルに置くほど、**壊れにくいが、失敗したときの原因特定が難しくなります。**
逆に下のレベルに置くほど原因は特定しやすいが、実装の変更で壊れやすくなります。

判断の順序はこうです。

1. **まず結合テストで書けないか考える。**モジュールをまたぐ実際の振る舞いを検証でき、
   内部構造を変えても壊れません。**ここが既定の置き場所です**
2. **分岐や境界値が多く、結合テストでは組合せが爆発する場合だけ単体テストに落とす**
3. **業務としての妥当性が問われるものは受入テストへ**（金額計算、帳票、業務フロー）
4. **性能・可用性・セキュリティはシステムテストへ**

### やってはいけない割り当て

- **全部を単体テストに寄せる** — 実装の内部構造に縛られ、リファクタのたびに壊れます
- **全部をシステムテストに寄せる** — 失敗しても原因が分からず、実行に時間がかかり、やがて誰も回さなくなります
- **同じ観点を複数レベルで重複して検証する** — 保守コストが倍になり、片方だけ直されて食い違います

## 検証の境界（どこで観測するか）

テストは**外から観測できる境界**で書きます。内部の関数を直接呼んで確認するテストは、
実装が変わるたびに書き直しになり、仕様の記録として役に立ちません。

境界の候補（上ほど望ましい）：

1. HTTP エンドポイント / CLI / 画面操作
2. アプリケーションサービスの公開インターフェース
3. モジュールの公開関数・公開クラス

**境界の数は少ないほど良い**です。テスト計画では、この案件で使う境界を明示してください。
新しい境界を増やす場合は、既存の境界で書けない理由を書きます。

## 非機能要件の扱い

機能テストとは別立てで計画します。

| 分類 | 検証方法の例 | 引き渡し先 |
| --- | --- | --- |
| 性能 | 負荷試験、応答時間測定 | `/design:14-performance-report` |
| 可用性 | 障害注入、切替試験 | システムテスト |
| セキュリティ | 観点レビュー、脆弱性診断 | `/design:08-security-review` |
| 運用保守 | 手順書に沿った復旧訓練 | `/design:12-release-migration-plan` |

**検証方法が決められない非機能要件は、要件として不完全です。**
`02` に戻って目標値と測定方法を定義し直してください。
