# RCA（根本原因分析）

**問題が起きたときにだけ実施する工程です。**順番を持ちません。

RCA が失敗する形は二つあります。

一つは**直接原因で止まること**。「null チェックが漏れていた」は直接原因です。
そこで止めると対策は「null チェックを入れる」になり、次は別の箇所で同じことが起きます。
**なぜそれが混入し、なぜレビューで見つからず、なぜテストで検知できなかったのか**まで辿ります。

もう一つは**人を原因にすること**。「担当者の確認不足」は原因ではありません。
確認不足が起きても事故にならない仕組みが無かったこと、が原因です。
**人ではなく仕組みを見ます。**個人の責任追及に転じた時点で、次から報告が上がってこなくなります。

分析手法は [ANALYSIS-METHODS.md](ANALYSIS-METHODS.md) を参照します。

## 共通ルール

0. **本スキルは文書のみを作成します。**修正コードの実装、暫定対応の実施は行いません。原因調査のためにコード・ログ・履歴を読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、対象範囲を把握します。案件に紐づかない障害の場合は保存先をユーザーに確認します。
2. **事実は自分で調べます。**ログ、コミット履歴、変更差分、issue、テスト結果。ユーザーには時系列の裏取りと、コードから読めない運用上の経緯だけ聞きます。
3. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。
4. **事実と推測を必ず書き分けます。**推測には「〜と推定される」と明記します。
5. 文体は敬体。図は mermaid。章立ては下記から増減しません。
6. 恒久対策はリスクとして `/design:09-risk-assessment` に、設計判断の変更は `/design:adr` に引き渡します。
7. 書き終えたら `00-index.md` の更新履歴に追記します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## 進め方

1. **事象を確定する** — 何が、いつから、どこで、どれだけ起きたか
2. **時系列を作る** — 発生・検知・一次対応・復旧。**検知が遅れたならその時間も記録します**
3. **直接原因を特定する** — 技術的に何が起きたか
4. **根本原因まで掘る** — なぜなぜ分析。**「なぜ検知できなかったか」の系統も必ず掘ります**
5. **暫定対応と恒久対策を分ける** — 止血と再発防止は別物です
6. **水平展開する** — 同じ原因が他にも潜んでいないか探します

## 成果物

`docs/design/<slug>/15-rca/YYYY-MM-DD-<incident>.md`
（`<incident>` は英語スラッグ。例：`2026-08-03-order-timeout.md`）

| 章 | 書くこと |
| --- | --- |
| 事象の概要 | 何が起きたか。3 行以内。 |
| 影響範囲 | 表：`対象 / 影響内容 / 件数 / 期間`。利用者影響、業務影響、データ影響。 |
| 時系列 | 表：`日時 / 事象 / 対応 / 対応者`。発生から復旧まで。**検知時刻を必ず含めます。** |
| 直接原因 | 技術的に何が起きたか。根拠となるログ・コードを添えます。 |
| 根本原因 | なぜなぜ分析の結果。混入の系統と、検知失敗の系統の両方。 |
| 検知が遅れた理由 | 監視・アラート・テストのどこが機能しなかったか。**即座に検知できていたなら「検知は機能した」と明記します。** |
| 暫定対応 | 止血として何がなされたか。副作用と、いつ解除するか。 |
| 恒久対策 | 表：`対策 / 種別 / 担当 / 期限 / 完了確認方法`。種別は `原因除去` `検知強化` `影響低減`。 |
| 再発防止の確認方法 | 対策が効いていることをどう確認し続けるか。 |
| 水平展開 | 同じ原因が潜む可能性のある箇所と、その確認結果。 |
