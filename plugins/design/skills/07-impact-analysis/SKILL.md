# 影響範囲分析

変更が**どこまで波及するか**を洗い出す工程です。`機能追加` モードでは最重要の成果物になります。

この工程の価値は、**コードベースを実際に調べて事実を積むこと**にあります。
「たぶんこのあたりに影響します」は分析ではありません。呼び出し元を検索し、
参照を辿り、依存を確認した結果を書きます。**推測で書くくらいなら「未調査」と書いてください。**

## 共通ルール

0. **本スキルは文書のみを作成します。**コードの実装・修正・実行は行いません。影響を洗い出すためにコードを読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、モードと対象範囲を把握します。無い場合は `/design:00-start` の実行を促して停止します。
2. `02-requirements-analysis.md` の `用語定義`、`05-architecture-design.md` の構成を読みます。
3. **影響の洗い出しは全てコードベース調査で行います。**ユーザーに「どこに影響しますか」と聞くのは禁止です。聞いてよいのは、コードから読み取れない運用・体制・外部都合だけです。
4. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。
5. 文体は敬体。図は mermaid。章立ては下記から増減しません。
6. 書き終えたら `00-index.md` のステータスを更新し、次工程を案内します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## 洗い出しの観点（全部見ること）

| 観点 | 調べ方 |
| --- | --- |
| 直接の呼び出し元 | 変更する関数・クラス・エンドポイントの参照を全件検索 |
| 間接の依存 | 呼び出し元のさらに呼び出し元。**2 段先までは必ず辿ります** |
| データ | スキーマ変更、移行の要否、既存データの互換性 |
| 外部連携 | API の入出力変更、連携先への影響、契約・仕様書の改訂要否 |
| 運用・監視 | ログ、アラート、バッチ、手順書、問い合わせ対応 |
| テスト | 壊れる既存テスト、追加が必要なテスト |
| 権限・セキュリティ | アクセス制御、監査ログへの影響 |

**影響度は 3 段階**（`大` / `中` / `小`）。判定基準を先に決めて全件に適用します。

## 成果物

`docs/design/<slug>/07-impact-analysis.md`

| 章 | 書くこと |
| --- | --- |
| 分析の目的と前提 | 何の変更を対象にした分析か。調査時点のコミット/ブランチも記録。 |
| 変更対象の一覧 | 表：`対象 / 変更内容 / 種別`。ここが起点になります。 |
| 影響を受けるモジュール・機能 | 表：`対象 / 影響内容 / 影響度 / 確認方法 / 対応要否`。**確認方法まで書いて初めて使える表になります。** |
| 影響を受ける外部システム | 表：`連携先 / 影響内容 / 事前調整の要否 / 調整先`。 |
| データへの影響 | スキーマ変更、移行手順の要否、ロールバック時のデータ整合。 |
| 運用・監視への影響 | 手順書、監視設定、問い合わせ対応の変更点。 |
| 後方互換性 | 互換性を壊すか。壊す場合の移行期間と告知。 |
| リリース順序 | 依存関係から導く順序。必要なら mermaid の `flowchart`。 |
| 影響範囲図 | `flowchart`。変更起点から波及先への矢印。影響度で色分け。 |
| 未調査の領域 | **調べきれなかった箇所を正直に書きます。**ここを空にするための嘘が最も危険です。 |
| 未決事項 | 決まらなかったこと。 |
