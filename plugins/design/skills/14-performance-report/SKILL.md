# 性能測定報告

**目標値との対比が無い性能報告に意味はありません。**「1.2 秒でした」だけでは、
それが良いのか悪いのか誰にも判断できません。`02` の非機能要件に書いた目標値を持ってきて、
一件ずつ `合格` / `不合格` を付けます。

もう一つ譲れないのが**測定条件の記録**です。データ量、同時実行数、環境、実行回数——
これが無い数値は再現できず、次回との比較もできません。**条件が揃わない測定値は報告に載せません。**

## 共通ルール

0. **本スキルは文書のみを作成します。**測定ツールの実装、負荷試験の実行は行いません。測定結果・ログ・プロファイル出力を読み解いて報告書にまとめるのが役割です。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、対象範囲を把握します。
2. `02-requirements-analysis.md` の `非機能要件` を読み、**目標値はそこから引きます。**該当する要件が無い場合は、報告前にユーザーと目標値を確認します。
3. `11-test-plan.md` の非機能検証方針、`06-poc/` に性能検証の PoC があれば読み、そのときの数値と比較します。
4. 測定環境・構成はリポジトリと設定から自分で調べます。測定値そのものはユーザーから受け取ります。
5. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。
6. 文体は敬体。図は mermaid。章立ては下記から増減しません。
7. 書き終えたら `00-index.md` の更新履歴に追記します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## 報告の原則

- **目標値を先に確定する。**測ってから基準を決めるのは、結果に合わせて基準を作ることです
- **代表値と併せてばらつきも記録します。**1 回だけの測定値は報告に載せません
- **代表値は中央値か p95 を使います。**平均値は外れ値に引きずられ、実際の体感とずれます
- **ボトルネックは推測で書かず、計測結果を根拠にします。**根拠が無い場合は「推定」と明記します
- **改善提案には見込み効果と実施コストを添えます。**両方無いと優先順位が付けられません

## 成果物

`docs/design/<slug>/14-performance/YYYY-MM-DD-<topic>.md`
（`<topic>` は英語スラッグ。例：`2026-08-03-search-api.md`）

| 章 | 書くこと |
| --- | --- |
| 測定の目的 | 何を確認するための測定か。対象の `NFR-ID` を明記。 |
| 目標値 | 表：`NFR-ID / 指標 / 目標値 / 出典`。**02 から引いた値であることを示します。** |
| 測定環境・条件 | 表：`項目 / 内容`。ハード構成、データ量、同時実行数、バージョン、測定回数。 |
| 測定シナリオ | 何をどう実行したか。再現できる粒度で。 |
| 測定結果 | 表：`指標 / 目標値 / 実測値(中央値) / p95 / 判定`。判定は `合格` / `不合格`。 |
| 結果の推移 | 前回測定がある場合の比較。必要なら mermaid で図示。 |
| ボトルネック分析 | 不合格項目について、どこで時間・資源を消費しているか。**計測に基づく根拠を添えます。** |
| 改善提案 | 表：`提案 / 見込み効果 / 実施コスト / 優先度`。 |
| 結論 | 目標を満たしたか。満たさない場合の次のアクション。 |
