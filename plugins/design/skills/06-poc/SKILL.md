# PoC（概念実証）の計画と報告

**必要なときだけ実施する工程です。**机上で判断できることに PoC は要りません。

このスキルが作るのは**文書**です。検証作業そのものは実施者が行います。
スキルの役割は 2 つに分かれます。

- **検証前** — 検証する疑問と**成功基準**を確定し、報告書の前半を作る
- **検証後** — 受け取った測定結果を読み解き、判定と考察を書いて報告書を完成させる

PoC が失敗する原因はほぼ一つ、**成功基準を先に決めないこと**です。
基準が無いと「動きました」で終わり、その結果が採用判断に使えません。
だから前半だけ先に作り、**検証に着手する前にユーザーに確認してもらいます。**

一つの PoC で検証するのは**疑問ひとつ**です。複数あるなら PoC を分けます。

## 共通ルール

0. **本スキルは文書のみを作成します。**検証用コードの実装や実行は行いません。既存コードや検証結果・ログを読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、モードと対象範囲を把握します。
2. `03-feasibility-study.md` `04-technical-investigation.md` の `検証が必要な項目` を読み、そこから検証対象を選びます。
3. `02-requirements-analysis.md` の `用語定義` に用語を合わせます。
4. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。**成功基準は必ず本人に確認します。**
5. 文体は敬体。図は mermaid。章立ては下記から増減しません。
6. 結果が採用判断につながったら `/design:adr` を、残課題が出たら `/design:09-risk-assessment` を促します。
7. 書き終えたら `00-index.md` のステータスを更新します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## 進め方

### 検証前（報告書の前半を作る）

1. **検証する疑問を一文で書く** — 「〜は実現できるか」「〜は目標値を満たせるか」
2. **成功基準を数値で決める** — 「レスポンス 200ms 以内」「1万件の取込が 5 分以内」
3. **検証範囲を絞る** — 疑問に答えるために**最小限**の範囲を定義します。作らないものも明記します
4. **測定条件を決める** — データ量、同時実行数、環境。ここを決めずに測ると再現できません

ここまで書いたらユーザーに提示し、**検証着手前に合意を取ります。**

### 検証後（報告書を完成させる）

5. **結果を受け取り、表に整理する** — 目標値と並べて `合格` / `不合格` を付けます
6. **考察を書く** — 数値が示していること。予想と違った点を必ず書きます
7. **判定する** — `採用` / `条件付き採用` / `不採用` の 3 値

## 成果物

`docs/design/<slug>/06-poc/<NN>-<topic>.md`
（`<NN>` は `01` からの連番、`<topic>` は英語スラッグ。例：`01-search-latency.md`）

| 章 | 書くこと | 作成時期 |
| --- | --- | --- |
| 検証の目的 | 答えを出したい疑問を一文で。出所（03 / 04 のどの項目か）も書きます。 | 検証前 |
| 仮説と成功基準 | 表：`項目 / 目標値 / 判定方法`。**検証着手前に確定します。** | 検証前 |
| 検証範囲 | 何を対象とし、何を対象外とするか。**対象外を明記します。** | 検証前 |
| 検証環境・条件 | ハード、データ量、同時実行数、バージョン。**再現に必要な情報を全部。** | 検証前 |
| 実施内容 | 実際に何が行われたか。必要なら mermaid で構成。 | 検証後 |
| 測定結果 | 表：`項目 / 目標値 / 実測値 / 判定`。生データも残します。 | 検証後 |
| 考察 | 数値が示していること。**予想と違った点を必ず書きます。** | 検証後 |
| 結論 | `採用` / `条件付き採用` / `不採用` と理由。条件付きなら条件を明記。 | 検証後 |
| 本番適用時の残課題 | PoC で対象外にしたもの。`09-risk-assessment` の入力になります。 | 検証後 |

## 次の工程

| 結論 | 次に実行するコマンド |
| --- | --- |
| `採用` — 設計に反映する | `/design:05-architecture-design` を更新 |
| `採用` — 設計は変わらない | `/design:09-risk-assessment`（残課題をリスク登録） |
| `条件付き採用` | 条件を `/design:09-risk-assessment` に登録してから先へ |
| `不採用` | `/design:04-technical-investigation` か `/design:03-feasibility-study` に戻る |
| 判断が採用可否を左右した | `/design:adr` |
