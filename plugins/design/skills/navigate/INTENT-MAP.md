# 意図とレポートの対応表

## やりたいこと → 必要なレポート

複数該当してよい。該当が無い／広すぎる場合は `/design:00-start` を案内する。

| やりたいこと | 必要なレポート（順） |
| --- | --- |
| 新しいシステム・サービスを立ち上げる | `01`→`02`→`03`→`04`→`05`→`08`→`09`→`10`→`11`→`12` |
| 既存システムに機能を足す | `01`→`02`→`07`→`09`→`10`→`11` |
| 小さな改修・不具合修正 | `02`→`07`→`11` |
| 「これは実現できるのか」を知りたい | `03` →（机上で足りなければ）`06` |
| 技術を選びたい・乗り換えたい | `04` →（検証が要れば）`06` → `adr` |
| 設計を整理・図にしたい | `05` |
| 何が壊れるか知りたい | `07` |
| セキュリティが不安 | `08`→`09` |
| 危なそうな点を洗い出したい | `09` |
| 作業を分担・見積もりたい | `10` |
| 品質をどう担保するか決めたい | `11` |
| 本番に出す準備をしたい | `12` |
| 上司・関係者に報告したい | `13` |
| 遅い・重いと言われた | `14` →（設計変更なら）`05`／（受容なら）`09` |
| 障害・不具合が起きた | `15`→`09` |
| 一区切りついたので振り返りたい | `16` |
| 決めたことを残したい | `adr` |

## 追加条件 → 絞り込み質問

最小セット（`02`・`05`／`07`・`11`）に**上乗せするかどうか**を決める判断材料。

左の「条件」が満たされるとそのレポートが必要になる。条件を自分で判断できない場合だけ、
右の質問をユーザーにする。**推奨案を添え、1 問ずつ、答えるたびに推奨を更新して見せる。**

| レポート | 追加する条件 | 聞く質問（推奨案） |
| --- | --- | --- |
| `01` 要求調査 | 要望の出所が複数人にまたがる／後で「言った言わない」になりそう | 「要望を出している方は複数いますか」（1 人なら不要） |
| `03` 実現可能性 | 実現できるか自体に不安がある、複数案から選ぶ | 「実現できるか不安な点はありますか」（無ければ不要） |
| `04` 技術調査 | 新しい技術・ライブラリ・外部サービスを採用する | 「今回、新しく採用する技術はありますか」（既存構成のみなら不要） |
| `06` PoC | 机上で判断できない数値・挙動がある | 「実際に動かさないと分からない点はありますか」（無ければ不要） |
| `08` セキュリティ | 個人情報・認証・権限・外部公開のいずれかに触る | 「個人情報の取り扱い、認証・権限、外部公開のいずれかに関係しますか」（**1 つでも該当なら実施推奨**） |
| `09` リスク評価 | 期限・体制・外部依存のいずれかに不安がある | 「期限や体制、外部の相手に不安はありますか」（**大きめの案件では実施推奨**） |
| `10` 開発計画 | 複数人で分担する、タスクが 10 件を超える | 「複数人で分担しますか」（1 人で数日なら不要） |
| `12` リリース・移行 | 本番リリースを伴う、データ移行がある、停止時間が発生する | 「本番リリースやデータ移行を伴いますか」（**伴うなら実施推奨**） |
| `13` 進捗報告 | 定期的な報告義務がある、期間が 2 週間を超える | 「定期的に報告する相手はいますか」 |
| `14` 性能報告 | 応答時間・処理件数などの性能要件がある | 「性能の目標値はありますか」（あれば `02` の非機能要件にも記載が必要） |
| `15` RCA | 問題が既に起きている | 質問不要。起きていれば実施、起きていなければ不要 |
| `16` 振り返り | 期間が長い、チームで進める | 「終わったあとに振り返りをしますか」 |

## 質問を作るときの禁則

- **要件そのものを聞かない。**利用者は誰か、どんな画面か、何を保存するか——これらは
  `/design:02-requirements-analysis` の仕事。ここで聞くと 02 で同じことをもう一度聞かれる
- **答えても推奨が変わらない質問をしない。**「どのくらいの規模ですか」のような、
  レポートの増減に直結しない問いは省く
- **環境から分かることを聞かない。**既存コードの有無、ブランチ名、既存文書の状態は自分で調べる
