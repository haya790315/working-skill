# 実現可能性調査

`02` で決めた要件が**そもそも実現できるのか**を、複数の案を比べて判断する工程です。

「できます」だけの報告書には価値がありません。価値があるのは
**「この案なら実現できるが、その代わり何を諦めることになるか」**です。
必ず 2 案以上を比較し、採らなかった案とその理由を残します。

## 共通ルール

0. **本スキルは文書のみを作成します。**コードの実装・修正・実行は行いません。調査のためにコードを読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、モードと対象範囲を把握します。無い場合は `/design:00-start` の実行を促して停止します。
2. `02-requirements-analysis.md` の `用語定義` を読み、用語はそこに合わせます。新しい用語を使う場合は 02 に追記します。
3. 調べられる事実は自分で調べます。ユーザーに聞くのは「判断」だけです。期限・体制・許容コスト感は必ず本人に確認します。
4. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。
5. 文体は敬体。図は mermaid。章立ては下記から増減しません。
6. 逆転コストが高く代替案が実在する判断が出たら `/design:adr` を促します。
7. 書き終えたら `00-index.md` のステータスを更新し、次工程を案内します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## 4つの評価軸

| 軸 | 見るもの | よくある落とし穴 |
| --- | --- | --- |
| 技術 | 実装できるか。既存構成と両立するか。 | 「ライブラリがある」＝実現可能、と早合点する |
| スケジュール | 期限に間に合うか。 | 開発だけ見て、レビュー・テスト・リリース調整を数えない |
| 体制・スキル | 作れる人がいるか。運用を誰が引き取るか。 | 作る人だけ数えて、保守する人を数えない |
| コスト | 相対的にどれだけかかるか。 | **金額は書きません。**相対比較（大/中/小）に留め、見積は別途 |

**判定は 3 値**にします。`実現可能` / `条件付きで実現可能` / `実現困難`。
`条件付き` の場合、その条件を必ず明記します。条件が書けないなら `実現困難` です。

## 成果物

`docs/design/<slug>/03-feasibility-study.md`

| 章 | 書くこと |
| --- | --- |
| 調査の目的 | どの要件の実現性を判断するのか。対象要件 ID を明記。 |
| 評価軸と判定基準 | 上記 4 軸。この案件で特に重視する軸があれば明記。 |
| 検討した案の一覧 | 表：`案ID / 概要 / 特徴`。**2 案以上必須。**「何もしない案」も比較対象として有効。 |
| 案ごとの評価 | 案ごとに 4 軸で記述。根拠となる事実（調べた結果）を必ず添えます。 |
| 評価マトリクス | 表：行が案、列が 4 軸 + 総合判定。一目で比較できる形に。 |
| 結論と推奨案 | どれを推すか、なぜか。**採らなかった案を採らない理由**も書きます。 |
| 前提条件とリスク | 推奨案が成立する前提。崩れたらどうなるか。詳細は 08 に渡します。 |
| 検証が必要な項目 | 机上では判断しきれず PoC が要るもの。`/design:06-poc` の入力になります。 |
| 未決事項 | 決まらなかったこと。 |
