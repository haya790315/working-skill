# 振り返り

**成果物ではなく、進め方を振り返る工程です。**何を作ったかは進捗報告の話です。
ここで見るのは、どう作ったか——見積は当たったか、手戻りはなぜ起きたか、次はどこを変えるか。

振り返りが形骸化する原因は一つ、**Try が実行されないこと**です。
「次はもっと早めに共有する」は Try ではありません。担当と期限が付いて、
次回の振り返りで実施状況を確認できるものだけを Try と呼びます。

## 共通ルール

0. **本スキルは文書のみを作成します。**コードの実装・修正・実行は行いません。実績確認のために履歴やコードを読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、対象範囲と工程の進捗を把握します。
2. **前回の振り返りがあれば必ず読み、`Try` の実施状況を確認します。**これを飛ばすと振り返りは儀式になります。
3. **事実は自分で調べます。**git 履歴、`13-progress/` の各報告、`15-rca/` の障害記録、issue の推移。調べた結果を提示してから、ユーザーに補ってもらいます。
4. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。
5. 文体は敬体。章立ては下記から増減しません。
6. 書き終えたら `00-index.md` の更新履歴に追記します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## KPT の書き方

| 区分 | 意味 | 判定基準 |
| --- | --- | --- |
| Keep | 続けること | **具体的な行動**であること。「チームの雰囲気が良かった」は Keep ではありません |
| Problem | 課題 | **事実に基づく**こと。感想ではなく、起きたことを書きます |
| Try | 次に試すこと | **担当・期限・確認方法が付く**こと。付かないなら Try ではありません |

Problem が全て Try に変換される必要はありません。**今は手を打たないと決めた Problem**は、
そう明記して残します。何も書かないより、判断を残すほうが価値があります。

## 定量で見る観点

感想だけの振り返りにしないため、下記は毎回数字で確認します。調べられるものは自分で調べます。

- 計画タスク数に対する完了数
- 見積規模（`S`/`M`/`L`）と実所要の乖離が大きかったタスク
- 手戻りが発生した箇所とその回数
- 期間中に発生した障害・不具合の件数（`15-rca/` から）
- 未決事項がどれだけ解消され、どれだけ残ったか

## 成果物

`docs/design/<slug>/16-retrospective/YYYY-MM-DD.md`

| 章 | 書くこと |
| --- | --- |
| 実施概要 | 表：`実施日 / 対象期間 / 参加者`。 |
| 実績サマリ | 期間中に何が進んだか。3 行以内。 |
| 前回 Try の実施状況 | 表：`前回のTry / 実施状況 / 効果`。前回が無ければ「初回」と明記。 |
| 定量指標 | 上記の観点を表で。前回との比較があれば併記。 |
| Keep | 続けたい具体的な行動。 |
| Problem | 事実に基づく課題。**なぜ起きたかまで一行添えます。** |
| Try | 表：`アクション / 担当 / 期限 / 効果の確認方法`。**3 件以内に絞ります。**多いと全部やりません。 |
| 対応しないと決めた Problem | 認識はしているが今回は手を打たないもの。理由も。 |
| 次回への申し送り | 次の期間・次の担当者へ伝えること。 |
