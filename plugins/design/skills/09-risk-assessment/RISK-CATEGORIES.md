# リスク分類チェックリスト

リスクの洗い出し漏れを防ぐための観点集です。**全分類に一度ずつ目を通し、
該当なしと判断した分類もその旨を記録**してください。「見ていない」と「見て無いと判断した」は違います。

## 技術リスク

- 未経験の技術・ライブラリを採用している
- 性能要件（応答時間・スループット・同時接続数）を満たせない可能性
- データ量の増加に耐えられない設計になっている
- 既存システムとの互換性・整合性が崩れる
- 障害時の復旧手順が確立していない、あるいは検証されていない
- 依存ライブラリのサポート終了・脆弱性
- 検証環境と本番環境の差異により、テストで再現しない問題が出る

## スケジュールリスク

- 見積の根拠が薄い作業がある
- 他チーム・他社の成果物を待つ工程がある
- 承認・稟議の所要期間を工程に織り込んでいない
- 繁忙期、長期休暇、他案件との重複
- 仕様が固まりきらないまま実装に入る前提になっている
- リリース日が外部要因（法改正、契約、キャンペーン）で動かせない

## 体制・リソースリスク

- 特定の担当者しか対応できない領域がある（属人化）
- 担当者の離任・異動の可能性
- レビュー担当が確保できていない
- 運用・保守の引き取り先が決まっていない
- 意思決定者が不在、あるいは決裁ルートが不明確

## 外部依存リスク

- 外部 API の仕様変更・サービス終了
- 外部 API のレート制限・障害
- ベンダー・委託先の遅延や品質
- クラウドサービスの障害・料金改定
- 連携先との事前調整が完了していない

## 品質リスク

- テストできない箇所がある（外部依存、タイミング依存）
- 既存のテストが不足していて、デグレを検知できない
- 非機能要件の検証手段が用意されていない
- レビュー観点が定まっていない

## セキュリティ・コンプライアンスリスク

- 個人情報・機微情報の取り扱いが増える
- アクセス制御の設計が既存方針と食い違う
- 監査ログの要件を満たせない
- 社内規定・業界規制・法令への抵触
- 脆弱性診断・セキュリティレビューの実施タイミングが遅い

## 運用リスク

- 監視・アラートが設計されていない
- 障害時の一次対応手順が無い
- ロールバック手段が無い、あるいは検証されていない
- 移行作業のダウンタイムが許容範囲を超える
- 問い合わせ増加への対応体制

## 事業・利用者リスク

- 利用者の業務手順の変更が必要で、周知・教育が要る
- 既存利用者に非互換な変更が及ぶ
- 期待した効果が得られなかった場合の撤退判断基準が無い
