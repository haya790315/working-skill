# リスク評価

起こりうる悪いことを先に並べ、**どう向き合うかまで決める**工程です。

リスク一覧が形骸化する原因は決まっています。**担当者と期限が空欄**だからです。
「対応策：注意深く進める」も同じく無価値です。誰が、いつまでに、何をするか——
そこまで書けないリスクは、書いていないのと変わりません。

網羅の観点は [RISK-CATEGORIES.md](RISK-CATEGORIES.md) を使います。

## 共通ルール

0. **本スキルは文書のみを作成します。**コードの実装・修正・実行は行いません。調査のためにコードを読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、モードと対象範囲を把握します。無い場合は `/design:00-start` の実行を促して停止します。
2. `02-requirements-analysis.md` の `用語定義` に用語を合わせます。
3. `03` の `前提条件とリスク`、`06-poc/` の `残課題`、`07` の `未調査の領域`、`08-security-review.md` の `検出事項` があれば全て読み、リスク候補として取り込みます。**下流工程が上流の宿題を拾うのがこの工程の役目です。**
4. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。担当者・許容度は必ず本人に確認します。
5. 文体は敬体。章立ては下記から増減しません。
6. 書き終えたら `00-index.md` のステータスを更新し、次工程を案内します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## 評価のしかた

**影響度**と**発生確率**をそれぞれ 3 段階（`高` `中` `低`）で判定します。
パーセンテージは使いません。偽の精度になるだけで、議論の役に立ちません。

リスクレベルは下表で機械的に決めます。

| 影響度 \ 発生確率 | 低 | 中 | 高 |
| --- | --- | --- | --- |
| **高** | 中 | 高 | 高 |
| **中** | 低 | 中 | 高 |
| **低** | 低 | 低 | 中 |

## 対応方針は 4 種類のみ

| 方針 | 意味 | 例 |
| --- | --- | --- |
| 回避 | リスクの原因ごとやめる | その機能を今回のスコープから外す |
| 低減 | 発生確率か影響度を下げる | 段階リリース、フィーチャーフラグ |
| 転嫁 | 他者に引き受けてもらう | マネージドサービス、保守契約 |
| 受容 | 受け入れる。**ただし検知手段を用意する** | 監視を追加し、閾値超過でエスカレーション |

**`受容` を選んだのに検知手段が無い場合、それは受容ではなく放置です。**
