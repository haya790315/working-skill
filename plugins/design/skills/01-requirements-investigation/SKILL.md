# 要求調査

**集める工程です。分析しません。**要望に優先度を付けたり、実現可能性を判断したり、
要件の形に整えたりするのは次工程（`/design:02-requirements-analysis`）の仕事です。

ここで分析を始めてしまうと、拾ったはずの要望が「実現できなさそう」という理由で
記録されないまま消えます。それが後の手戻りの最大の原因になります。**判断せずに全部記録します。**

## 共通ルール

0. **本スキルは文書のみを作成します。**コードの実装・修正・実行は行いません。調査のためにコードを読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、モードと対象範囲を把握します。無い場合は `/design:00-start` の実行を促して停止します。
2. 調べられる事実（コードベース・既存ドキュメント・issue・仕様書）は自分で調べます。ユーザーに聞くのは「判断」だけです。
3. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。
4. `機能追加` モードでは対象を既存システムへの差分に限定します。既存仕様は前提として扱い、再定義しません。
5. 文体は敬体。図は mermaid。章立ては下記から増減しません。
6. 書き終えたら `00-index.md` のステータスを更新し、次工程を案内します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## 調査の進め方

1. **情報源を洗い出す** — issue、既存ドキュメント、コード内のコメント、過去の議事録、ユーザーの発言。
2. **現状を事実として記録する** — 「今どうなっているか」。あるべき姿ではありません。
3. **要望を発言単位で拾う** — 言い換えず、出典を残します。矛盾する要望も両方載せます。
4. **確認できなかったことを明示する** — 「聞けていない」ことも成果物です。

## 成果物

`docs/design/<slug>/01-requirements-investigation.md`

| 章 | 書くこと |
| --- | --- |
| 調査の目的 | 何を明らかにするための調査か。2〜3 行。 |
| 調査方法・情報源 | 何を読み、誰に聞いたか。表で列挙。 |
| ステークホルダー一覧 | 表：`役割 / 立場 / 関心事 / 決裁権の有無`。 |
| 現状の業務・システム | 今どう回っているか。必要なら mermaid で現行フロー。 |
| 収集した要望一覧 | 表：`ID / 提起者 / 要望内容 / 背景・理由 / 出典`。ID は `REQ-01` から連番。 |
| 挙がった制約・前提 | 期限、既存システム、法令、社内規定など。 |
| 未確認事項 | 聞けていない・裏が取れていないこと。誰に確認すべきかも書きます。 |
| 未決事項 | この工程で決まらなかったこと。 |

要望 ID（`REQ-01`…）は次工程の要件と対応付けるために使います。**必ず採番します。**
