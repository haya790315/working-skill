# アーキテクチャ設計

システムの**骨格**を決める工程です。何をどう分けて、どこで境界を引き、何がどこと話すのか。

この工程の成果物の良し悪しは、**図が主・文章が従になっているか**で決まります。
構成を文章だけで説明した設計書は、書いた本人以外読めません。まず mermaid で描き、
図から読み取れないことだけを文章で補います。

決定の密度が最も高い工程でもあります。**判断するたびに ADR 候補かどうかを自問してください。**

## 共通ルール

0. **本スキルは文書のみを作成します。**コードの実装・修正・実行は行いません。調査のためにコードを読むことはします。
1. 開始時に `docs/design/<slug>/00-index.md` を読み、モードと対象範囲を把握します。無い場合は `/design:00-start` の実行を促して停止します。
2. `02-requirements-analysis.md` の `用語定義` を読み、コンポーネント名・テーブル名は用語定義に合わせます。新しい用語を使う場合は 02 に追記します。
3. `03` `04` があれば読み、そこで決めた方針を前提とします。
4. 既存の構成はコードベースから自分で調べます。ユーザーには聞きません。
5. 質問は 1 回に 1 問、推奨案を添えます。上限 6 問（超える分は推測で埋めず、未解決として明記）。
6. `機能追加` モードでは全体構成を描き直さず、**差分（追加・変更されるコンポーネント）を強調表示**します。既存部分は文脈として薄く描きます。
7. 文体は敬体。章立ては下記から増減しません。
8. 逆転コストが高く代替案が実在する判断が出たら、その場で `/design:adr` を促します。
9. 書き終えたら `00-index.md` のステータスを更新し、次工程を案内します。

### 質問の帰属

**この工程の担当でない問いに、その場で答えを出さないでください。**

- **前工程で決まっているべきこと** → その工程の成果物に戻って追記し、`00-index.md` の更新履歴に記録します
- **後工程で決めること** → `未決事項`（この文書に無ければ課題を記す章）に、**どの工程が決めるか**を添えて残します

前工程の漏れを黙って埋めると、その判断は誰にも共有されないまま下流へ流れます。
後工程の問いをここで決めると、その工程が持っている情報を使わずに決めたことになります。

## 必須の図（すべて mermaid）

| 図 | 記法 | 描くもの |
| --- | --- | --- |
| システム構成図 | `flowchart` | コンポーネントと外部システム、その間の通信 |
| ER 図 | `erDiagram` | エンティティ、属性、関連。**用語定義と名前を揃えます** |
| シーケンス図 | `sequenceDiagram` | 主要ユースケースの処理の流れ。全部ではなく代表 2〜3 本 |

## 成果物

`docs/design/<slug>/05-architecture-design.md`

| 章 | 書くこと |
| --- | --- |
| 設計方針 | 何を最優先に設計したか。3 点以内。トレードオフを明示。 |
| システム全体構成 | `flowchart`。`機能追加` の場合は変更箇所を強調。 |
| コンポーネント構成と責務 | 表：`コンポーネント / 責務 / 依存先`。**責務は一文で書けること。**書けないなら分割が足りていません。 |
| データモデル | `erDiagram` + 表：`エンティティ / 説明 / 主要属性`。 |
| 主要処理フロー | `sequenceDiagram` を 2〜3 本。異常系を最低 1 本含めます。 |
| 外部インターフェース | 表：`I/F名 / 相手 / 方式 / 用途`。API・イベント・バッチ連携。 |
| 非機能要件への対応方針 | 表：`NFR-ID / 要件 / 対応方針`。**02 の非機能要件を全件埋めます。**空欄があるなら設計が足りていません。 |
| 採用技術スタック | 表：`分類 / 技術 / 選定理由 / 関連ADR`。 |
| 関連 ADR | この工程で起票した ADR の一覧。 |
| 未決事項 | 決まらなかったこと。 |
