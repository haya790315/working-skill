# run-ticket — 票的整理與寫回

兩個流程：**A. 開工整理**（只讀）、**B. 完工寫回**（會寫票，一定先確認）。
平台操作（找票、讀票、更新、開票）見 [PLANE.md](PLANE.md)。換平台時只換這一層，流程不變。

語言：給使用者看的整理用**中文**；寫進票的內容**跟原票同語言**。

## Step 0 — 找到票

依序：使用者給的票號 → 網址 → 從目前分支名稱推斷（如 `tumiki-203-xxx`）→ 都沒有就問。

## 流程 A — 開工整理（要詳細）

目標：使用者讀完就掌握**背景、現在的問題、要改善的點、修改方向**，可以直接動手。

1. **讀票的整條脈絡**：票本身、父票、同父票的兄弟票、票內提到的其他票。
2. **讀程式碼**：票上提到的檔案、相關 `git log`、PR。Outline／Slack **只在票或專案描述有附連結時**才讀。
3. **對照現在的 main**：實際確認「現在的行為」，票上寫的路徑、行號、行為若已不符，列出來。
4. **在對話中輸出整理**（格式見 [BRIEF.md](BRIEF.md)）。推測一律標「推測」，並寫出依據。
5. **票本身缺「目的／為什麼」時**，問使用者要不要補一段到票上。只寫查證過的事，經使用者同意才寫。

## 流程 B — 完工寫回（要簡潔）

目標：同事**只看票**就知道處理了什麼、怎麼處理的、現在是什麼狀態，不用去看 code。

1. **收集做了什麼**：`git diff main...HEAD`、commits、PR（`gh pr view`）、本次對話，以及票上原本的「要做的事」。
2. **判斷票的類型，選主體寫法**，見 [TEMPLATES.md](TEMPLATES.md)。
3. **未対応・要検討 逐項問**：「這項要開票嗎？」要開 → 父票設成跟原票相同，新票內容要單獨看得懂（背景＋要做什麼），開好後把票號填回清單。
4. **給使用者確認**：貼出要寫入的完整區塊，並用一句中文說明「判斷為○○類型，所以用△△寫法」。**同意前不 update。**
5. **寫回**：原文一字不動；在最後加上區塊，重跑時只替換自己的區塊（作法見 PLANE.md）。
6. **不改票的狀態**（State）。

### 寫回的原則

- **整個區塊控制在一個畫面內**（約 20 行以內），一行只講一件事。寫不下就是寫太細。
- 寫給**沒看過 code 的同事**：寫行為與結果，不寫函式內部。檔名、API 名稱只在同事需要知道時才寫。
- **`対応方針` 一定要寫**：1～3 行，說明怎麼處理的（例如「名簿を1回で取って画面側で数える形に変えた」）。
- `仕組み` 只在做法不直觀、光看対応方針無法理解時才補，**最多 3～5 行**，或一條 `A → B → C` 的流程。
- Before/After 寫**使用者／呼叫端看得到的差異**，一項一行。
- `補足（他の人向け）` 只放會影響別人的事：回傳值改了、前提假設、上限值。
- `未対応` 每項都要有**為什麼沒做**和**下一步**（票號或「要誰決定」）。
- 不寫過程（「一開始試了 X」）。只有結論和理由。

## 交付前自檢

- [ ] A：背景、現在的問題、要改善的點、修改方向都有寫，而且具體到可以動手
- [ ] A：推測都有標，而且有依據；過期資訊已對照 main 確認
- [ ] B：一個畫面看得完；不看 code 也懂做了什麼、怎麼做的
- [ ] B：原文沒被改到；重跑時沒有重複堆疊區塊
- [ ] B：每個未対応都有理由和下一步；寫入前使用者已經同意
