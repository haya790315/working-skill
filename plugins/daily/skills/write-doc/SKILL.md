# write-doc — 文档撰写

**只产出文档。**不实装、不改业务代码；为确认事实会读代码与配置。
**只管书写风格与内容取舍。**目录、命名、模板遵从项目既有规范。

## Step 1 — 先找规范与模板（不可跳过）

按顺序找，找到就停：

1. **项目规范** — `docs/README.md`、`CLAUDE.md`、该目录自己的 `README.md`。
   提取：章节职责分工、目录与命名规则、语言与文体（敬体／常体）、明文禁止事项。
2. **同类既有文档** — 要写的东西旁边有没有同类型的文件？有就照它的骨架、文体、标题层级。
3. **既有 skill 模板** — 写 ADR 时，采番・目录・模板・起票判定一律以 `/design:adr` 为准，不在这里另造一套。
4. 三者都没有 → 自己组一个最小骨架，并在交付时说明「项目没有既有规范，我用了什么」。

项目规范与本 skill 冲突时，**以项目为准**，并写一行说明依从了哪一条。

## Step 2 — 分岔：新写还是改写

### 改写既有文档 — 先出清单，等点头再动手

```
【改写前确认】docs/00-開発ガイド/初回セットアップ.md

削除（来历）  ：L12-15「当初は〜を検討したが」
移動          ：L80-120 の運用手順 → docs/07-運用ガイドライン/
書き換え（構造）：L40-60 の五段落 → 表格
触らない      ：コマンド内の実値（事実は動かさない）

→ これで進めてよいか？
```

- **事实要改**（数值、步骤、结论）→ 单独提出来问，不混进结构调整里。
- 点头之前不写文件。

### 新写 — 篇幅大才先给骨架

跨多个章节、或 H2 会超过三四个时，先给「标题 + 每行一句『这节回答读者的什么问题』」让使用者过目。
只有两三节的小文档直接写。

## Step 3 — 取材：只信代码，不信对话

- 事实来源 = 代码、配置、CI 定义、既有文档、实际执行结果。
- **本次会话讨论过的内容，只能用来决定「写什么结论」，不能搬进文档。**
- 验证不了的事不写进文档，列成 `未確認` 交还使用者。

## Step 4 — 写

| 关注点 | 规则在哪 |
| --- | --- |
| 留什么删什么、用语、标题、段落 | [STYLE.md](STYLE.md) |
| 命令、变量、GUI 步骤 | [COMMANDS.md](COMMANDS.md) |

## Step 5 — 交付前自检

- [ ] 没有「谁、何时、经过什么讨论、曾经考虑过什么」——来历全删，因果留下
- [ ] 每个标题单看就知道那一节在讲什么
- [ ] 这个文件只回答一类问题；其余的已经移到该去的章节并留了一行链接
- [ ] 命令区：变量一览表 + 可整段 copy 的定义块，后续命令零硬编码
- [ ] 要动手改的位置都有 `← 要変更`，且集中在定义块上半部
- [ ] GUI 步骤写到不看画面也知道要点哪里，取得的值有说明填回哪个变量
- [ ] 文体、用语、目录与项目既有文档一致

## 交付时一并说明

1. 依从了项目的哪条规范（或「没有既有规范，我用了什么」）
2. 改写时实际删掉了什么
3. `未確認` 清单
